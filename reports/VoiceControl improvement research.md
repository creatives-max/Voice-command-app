# Make VoiceControl verify, listen better, and speak less

Fix three things first, in this order. First, protect the app on Google Play: since the October 2025 policy update, using the Accessibility API to "autonomously initiate, plan, and execute actions" is banned unless the app is a declared accessibility tool, so the Claude "do it for me" agent is exactly what Google is targeting ([Play Console Help](https://support.google.com/googleplay/android-developer/answer/10964491?hl=en)). Second, make the agent more accurate by checking every action in code. Published studies credit big gains to three things the app does not yet do: checking the result after each action, keeping a written plan across steps, and giving the agent notes about each app. Removing the planning part cut success on hard tasks from 61.4% to 29.5%, removing post-action checking cost 15 points, and per-app notes took one agent from 2.2% to 73–96% ([Mobile-Agent-v2](https://arxiv.org/html/2406.01014v1); [Minitap](https://arxiv.org/html/2602.07787v1); [AppAgent](https://arxiv.org/html/2312.13771)). Third, make it faster and cheaper. Shrink the screen text sent to Claude, run Claude at `low` effort, stream the reply so speech starts early, replay known screens without calling the model, and move the backend off Render's free plan, which sleeps after 15 minutes and takes about a minute to wake ([Render](https://render.com/docs/free)). For speech, the biggest cheap win is matching what the recognizer heard against the button names on screen, in any script, using every alternative transcript the recognizer returns. Sarvam's recognizer is the best cloud backup for Hinglish at ₹30 per hour of audio ([Sarvam pricing](https://docs.sarvam.ai/api/pricing)). The market gap is still open. Google Voice Access lists no Indian language, and Gemini's app-operating agent launched in English only, in the US and Korea, and only for a handful of apps ([Google Support](https://support.google.com/accessibility/android/answer/6151848?hl=en); [9to5Google](https://9to5google.com/2026/02/25/gemini-automation-android/)). VoiceControl's advantage is Indian languages, help designed for seniors, and safety, so the plan below spends effort there.

## Google Play's October 2025 rule is the top risk

All the accuracy work is wasted if the app is removed from Play, so policy comes first. Google's current Accessibility API policy says **"any use of the Accessibility API that enables an app to autonomously initiate, plan, and execute actions or decisions is strictly prohibited."** There are two exceptions. Apps that declare `isAccessibilityTool="true"` may use autonomous features if those features serve their core purpose of helping people with disabilities. And any app may run **deterministic, rule-based automation that follows a fixed script a person defined** ("if X happens, do Y") ([Play Console Help](https://support.google.com/googleplay/android-developer/answer/10964491?hl=en)). The same page names **"voice-based input systems" as a qualifying accessibility tool, and "automation tools" and "assistants" as not qualifying**. Google announced the update on 30 October 2025. The effective date is unclear in the sources: one secondary summary gives 28 January 2026, while Google's page promises at least 30 days of notice ([Play Console Help 16550159](https://support.google.com/googleplay/android-developer/answer/16550159)). Google has a history of tightening this API, from the 2017 removal threats to the 2022 call-recording ban ([XDA](https://www.xda-developers.com/google-trying-limit-apps-accessibility-service/); [Engadget](https://www.engadget.com/google-is-banning-third-party-call-recording-apps-from-the-play-store-093201443.html)).

Here is what that means for each part of the app. Voice commands and recorded-flow replay are on safe ground: one is voice input, the other is a script a person defined. Smart-mode form filling, where the user answers each question, is probably fine. The Claude agent that plans and taps on its own is what the policy targets. I see three ways to handle it; this is my reading of the policy, not a Google ruling, so get a policy review before you choose. **Option A:** present the app as what it truly is, a voice-input accessibility tool for people whose eyesight, hands, age or reading ability make phones hard to use, and declare `isAccessibilityTool`. The cost is that store listing, onboarding and features must stay focused on disability. Generic "assistant" features weaken that claim. **Option B:** keep a human in the loop. The agent says its plan ("Pehle WhatsApp kholungi, phir Rahul ko dhundhungi, phir message likhungi — theek hai?"), the user approves it, and every action then follows from the user's request. No source confirms that Google treats this as "not autonomous." **Option C:** ship the autonomous agent only in a sideloaded build. In any case, if the app does not declare itself an accessibility tool, it needs an in-app **prominent disclosure with affirmative consent**, shown during normal use and separate from other notices, plus a video for the Permission Declaration Form ([Play Console Help](https://support.google.com/googleplay/android-developer/answer/10964491?hl=en)). My advice: build Option B's plan read-back now. It also improves accuracy, as the next section shows, and it fits Option A as well.

Policy and safety overlap, because the users are prime fraud targets. "Digital arrest" scam reports to India's national cyber-crime portal (NCRP) tripled from 39,925 in 2022 to 123,672 in 2024, and **losses grew from about ₹91 crore to ₹1,935 crore** ([IndiaSpend](https://www.indiaspend.com/data-viz/dataviz-how-indias-cyber-crime-incidence-is-rising-972933)). In a test of 50 attacks that hide instructions in on-screen text (prompt injection), mobile agents **blocked only 3–15**, and GPT-4o spotted 92% of hazards when simply asked about them but prevented only 36% when acting as an agent ([MobileSafetyBench](https://arxiv.org/html/2410.17520v3)). The app already confirms before pay or send and leaves PIN, OTP and passwords to the user. Add three protections it does not have yet. First, mark all on-screen text and incoming messages as untrusted data in the prompt, and never act on instructions found in them. Second, add a code-level scam check that pauses and warns when a payment, screen-sharing or app-install request comes during or soon after a call from an unknown number, and that blocks the agent from opening remote-access apps such as AnyDesk. Third, add a caregiver option. NPCI's **UPI Circle** already lets a family member approve each payment, or set caps of ₹5,000 per transaction and ₹15,000 per month ([Razorpay](https://razorpay.com/blog/what-is-upi-circle/)). Guiding seniors to set it up is cheaper and safer than building approval rails yourself. Do not let the model alone decide what is risky: an automatic risky-action detector reached only **75% precision and 80.5% recall** ([AutoDroid](https://arxiv.org/html/2308.15272v4)). Keep a fixed list of risky words and banking/UPI app package names alongside the model's own flag. Also copy Gemini's always-visible "agent is working — tap to stop" bar ([9to5Google](https://9to5google.com/2026/02/25/gemini-automation-android/)). For seniors, a big stop button works better than trying to talk over the phone.

## Code checks after each step are the biggest accuracy gain

VoiceControl's design is sound. It sends the accessibility tree as text, makes one Claude call per step, and returns a JSON action. That matches the setup that won in Google's AndroidWorld paper: **text only scored 30.6%, versus 25.4% for the same agent given screenshots** ([AndroidWorld](https://arxiv.org/pdf/2405.14573)). Top systems now report 91–100% on AndroidWorld, so the benchmark is nearly maxed out ([benchmarklist](https://benchmarklist.com/benchmarks/androidworld/)). Those scores did not come from single-call text agents. They came from stronger models plus **separate planning, checking and reflection steps**. The Minitap paper (100% on AndroidWorld) measured what each part was worth: post-action checking **−15 points** when removed, one action at a time with instant failure detection −12, screenshot plus tree −11 ([Minitap](https://arxiv.org/html/2602.07787v1)). Its lesson suits VoiceControl: models are good at understanding goals and weak at reliable execution, so **check results with plain code, not with more model calls**. Its failure breakdown also matters: **41% of failures were execution problems, including text that silently failed to type**, and 38% were context problems such as stale screen trees ([Minitap](https://arxiv.org/html/2602.07787v1)).

These are the accuracy changes I would make, most valuable first. **Check every action in code.** Compare the screen tree before and after each action, and add one line to the next prompt such as "last action: tapped 'Search' → screen changed, keyboard open" or "typed 'Rahul' → field still empty." For typing, read the field back. If the text is missing or wrong, retry with a set-text call or clear and retype. This also extends your loop detection: the current check catches repeated identical actions, while a "no change" result catches an action that did nothing, even when the next action differs. **Add a plan field and a notes field to the JSON**, carried forward each step. The plan holds sub-goals and progress. The notes hold values read from earlier screens, such as amounts, names or an order number. Removing planning was the single biggest loss in Mobile-Agent-v2: success on hard tasks fell from **61.4% to 29.5%**, and removing reflection cut it to 45.5% ([Mobile-Agent-v2](https://arxiv.org/html/2406.01014v1)). **Require proof before DONE.** The model must quote the on-screen text that shows the task is finished, such as "Message sent" or a tick next to the message. Stopping too early or too late caused 52% of errors in Mobile-Agent-v2 and still 12% after Mobile-Agent-E's self-learning fixes ([Mobile-Agent-E](https://arxiv.org/html/2501.11733)).

**Next, give the agent short notes about each app, and learn them from your flows.** In AppAgent, success went from **2.2% with no notes, to 73.3% with notes from exploring the app, 84.4% with notes from watching demos, and 95.6% with hand-written notes** ([AppAgent](https://arxiv.org/html/2312.13771)). Mobile-Agent-E's saved "tips" and "shortcuts" raised satisfaction from 75.1% to 86.9% ([Mobile-Agent-E](https://arxiv.org/html/2501.11733)). VoiceControl already saves flows after jobs. Turn each finished job into two or three lines for that app ("PhonePe: Pay button is bottom-right after entering amount"), and add them to the prompt whenever that app is in front. Also write a short guide to common Android patterns: close pop-ups first, wait while a loading spinner shows, and check before claiming done. Rich guidance is most of why Google's full M3A agent beat its simple version, **30.6% vs 19.8%**, using the same model ([AndroidWorld](https://arxiv.org/pdf/2405.14573)). **Add a screenshot only when the tree is thin**: few labelled nodes, a WebView, or unlabelled icon buttons. In Google's tests, screenshots won only on web-content tasks, where the tree is often incomplete (67.7% vs 59.7%) ([AndroidWorld](https://arxiv.org/pdf/2405.14573)). Payment pages and Indian apps built with hybrid frameworks are often exactly these screens. A newer idea is worth trying: V-Droid builds a list of candidate actions from the tree and has the model *score* them instead of writing an action. It reported **59.5% on AndroidWorld at 0.7 s per step** ([V-Droid](https://arxiv.org/abs/2503.15937v3)).

These numbers do not compare across benchmarks, and single runs vary by about ±4 points ([AndroidWorld](https://arxiv.org/pdf/2405.14573)). I found no published AndroidWorld result for a recent Claude model using the tree alone. Your live test harness is the right way to measure. Before and after each change above, run the same 20–30 Hinglish tasks several times.

## Fewer tokens and a backend that never sleeps cut seconds and rupees

Model choice and output length drive speed; screen size drives cost. Per the notes' check of Anthropic's docs, current prices are **Opus 5.5 $4/$20 and Sonnet 5.5 $2/$10 per million input/output tokens**, and cache reads cost $0.20 on both ([Models overview](https://platform.claude.com/docs/en/about-claude/models/overview.md); [Pricing](https://platform.claude.com/docs/en/about-claude/pricing.md)). A rough estimate for one agent step on Opus 5.5 assumes a 1.5k-token system prompt, about 3k tokens of screen JSON, about 1.5k of history and about 400 output tokens. That comes to **about $0.03 per step whether or not caching is used**. The fresh screen JSON dominates, and output tokens cost five times as much as input. Treat this as an estimate; measure it with `usage` and the `count_tokens` endpoint. It changes the priorities: **shrinking the screen JSON and the output saves more than caching does.** Remove invisible, off-screen and decorative container nodes; replace resource IDs with short numbers such as `#12` and keep the mapping on the server; cut long texts to about 80 characters; and show only the first N items of long lists, with a "+K more" marker. One mobile agent cut a roughly 40k-token raw tree to about **339 tokens per prompt** this way, and its accuracy held ([AutoDroid](https://arxiv.org/html/2308.15272v4)).

Caching still helps when placed well. Opus 5.5 and Sonnet 5.5 cache prompts from **512 tokens**, so the system prompt qualifies. Put one cache breakpoint at the end of the fixed system prompt, and use automatic caching for the growing history. Do not put a breakpoint on the screen block, because writing to cache costs 1.25× normal input. Keep the system prompt byte-for-byte the same, and put dynamic details such as the date in later messages ([Prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching.md)). When the server boots and when the user opens the assistant, send a `max_tokens: 0` request to warm the cache. Anthropic recommends this for voice apps ([Prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching.md)). **Use one fixed output schema.** Changing `output_config.format` throws away the cache, and a new schema adds a one-time compile delay ([Structured outputs](https://platform.claude.com/docs/en/build-with-claude/structured-outputs.md)). Structured outputs without tool definitions also avoid the hidden **286-token** tool prompt ([Pricing](https://platform.claude.com/docs/en/about-claude/pricing.md)). Note two API rules: on these models, forcing `tool_choice` or prefilling the assistant's reply returns an error 400.

For speed, run Opus 5.5 at **`low` effort**. Anthropic describes `low` as giving "significant token savings with some capability reduction" for tasks where speed matters. Keep effort the same throughout a conversation, because changing it clears the cache ([Effort](https://platform.claude.com/docs/en/build-with-claude/effort.md)). Then test **Sonnet 5.5 at low effort**, which costs half as much and is labelled "Fast" instead of "Moderate." Anthropic's guidance is to test the stronger model at lower effort before building a system that switches between models. Each model keeps its own cache, so switching mid-task loses the cached history. Use the cheaper model for separate one-off calls, such as interpreting a single sentence or writing a form-field question. **Do not adopt Haiku 4.5.** It cannot cache a prompt under 4,096 tokens, it does not support `effort`, and it may be retired as early as **15 October 2026** ([Models overview](https://platform.claude.com/docs/en/about-claude/models/overview.md)). **Stream the response and put a short `say` field first** in the schema, so speech and the action can start before the full JSON arrives ([Structured outputs](https://platform.claude.com/docs/en/build-with-claude/structured-outputs.md)). Better still, skip the model entirely on familiar screens. Store a fingerprint for each screen: the app, the activity, a hash of the button labels, and the goal. Save the action that worked there. On a match, check the target button still exists and do it with no model call. AutoDroid's reuse of known paths worked in 75% of cases and cut the number of model calls ([AutoDroid](https://arxiv.org/html/2308.15272v4)).

The backend is the cheapest fix of all. **Render Free sleeps after 15 minutes without traffic and takes "about one minute" to wake, on 0.1 CPU** ([Render](https://render.com/docs/free)). That fully explains a 50–100 second first command after a quiet spell. An outside ping every 10–14 minutes keeps it awake within the 750 free hours. But Render can suspend free services with "uncommonly high" traffic, and 0.1 CPU slows a Java/Kotlin (JVM) server even when awake.

| Option | Monthly cost | Notes |

| Render Free + external ping | $0 | 0.1 CPU; suspension risk ([Render](https://render.com/docs/free)) |
| Fly.io shared-cpu-1x 512MB / 1GB | $3.69 / $6.70 | Always on ([Fly.io](https://docs.fly.io/about/pricing)) |

Seven dollars a month buys about 220 Opus steps at $0.03 each. One avoided one-minute wait per user is worth far more. Move to a $4–7 always-on plan, have the app call a `/warmup` endpoint when the assistant opens, and consider Java startup tuning (class-data sharing, or GraalVM native-image) to cut startup time.

## Hinglish recognition improves most from on-screen words and n-best matching

Indian-trained speech models clearly beat general cloud services on published Hindi tests. On AI4Bharat's Vistaar benchmark, **IndicWhisper averages 13.6% word error rate (WER) in Hindi, versus 23.9% for Google STT and 20.0% for Azure** ([Vistaar](https://github.com/AI4Bharat/vistaar)). Those Google and Azure numbers date from about 2023 and predate Chirp 3, so treat them as old. Sarvam reports **11.81% Hindi WER** for Saarika v2.5 and markets it for code-mixed speech with automatic language detection ([Sarvam docs](https://docs.sarvam.ai/api-reference-docs/models/saarika)). Its successor, Saaras V4 (September 2026), claims streaming first output under 150 ms and support for 22 languages with code-mixing. Sarvam has published no head-to-head error numbers against competitors ([Sarvam blog](https://www.sarvam.ai/blogs/introducing-saaras-v4)). Prices: **Sarvam ₹30 per hour, versus Google STT v2 at $0.016 per minute (about ₹84 per hour)** ([Sarvam pricing](https://docs.sarvam.ai/api/pricing); [Google pricing](https://cloud.google.com/speech-to-text/pricing/)). Deepgram Nova-3 handles Hindi–English mixing, but no other Indian language, and developers report it sometimes mistakes Hinglish for Spanish ([Deepgram](https://deepgram.com/learn/hinglish-voice-ai-speech-recognition)). For Hinglish across all target languages, Sarvam is the strongest cloud choice.

Do not replace Android's `SpeechRecognizer` yet. It is free, it streams, and it can run on the phone. Get more out of it first. Pass the current screen's button labels and the user's app names in `EXTRA_BIASING_STRINGS`. Ask for several alternative transcripts with `EXTRA_MAX_RESULTS`, and turn on `EXTRA_PARTIAL_RESULTS` ([RecognizerIntent](https://developer.android.com/reference/android/speech/RecognizerIntent)). Google warns that recognizers may ignore these settings, and the notes conflict on which Android version added biasing and language switching (the notes suggest 33/34), so check in the IDE and test on cheap phones. The bigger win is in your own code. Convert both the transcripts and the on-screen labels to plain Latin letters (ICU `Any-Latin`, or IndicXlit), then fuzzy-match them, so "व्हाट्सएप" and "whatsapp" both match "WhatsApp." Score every alternative transcript as recognizer confidence × label match. Act above a high threshold, ask "WhatsApp?" in the middle band, and ask again below it. Some recognizers return no confidence scores, so plan for that. Sarvam V4's keyword-prompting result (**16.03% WER** on its context test) suggests that adding context like this measurably helps Indian-language recognition ([Sarvam blog](https://www.sarvam.ai/blogs/introducing-saaras-v4)). Use the cloud only as a backup. When match scores stay low, or the phone has no language pack for the user's language, send the saved audio to Sarvam. On mid-range and high-end phones, an offline choice is AI4Bharat's IndicConformer, at **131 MB per language** in a compressed build, though the 600M model needs about 1 GB of RAM ([HF](https://huggingface.co/nmukthap/vertexvoice-indic); [HF int8](https://huggingface.co/yashwork-byte/indic-conformer-600m-int8-onnx)).

For voice output, keep Android TTS as the default and save audio for common phrases. Cloud Indian voices cost about the same per character: **Sarvam Bulbul v3 at ₹30 per 10k characters, Google Chirp 3 HD at $30 per million, Azure neural at about $15 per million** ([Sarvam pricing](https://docs.sarvam.ai/api/pricing); [Google TTS pricing](https://cloud.google.com/text-to-speech/pricing/); [costbench](https://costbench.com/software/ai-voice-tools/microsoft-speech/)). A 40-character confirmation costs a fraction of a rupee, and saving audio for fixed phrases removes most of that. The open models, Indic Parler-TTS (Apache-2.0, 22 languages) and IndicF5, need a server GPU and cannot run on the phone ([HF](https://huggingface.co/ai4bharat/indic-parler-tts)). I found no listening-quality (MOS) scores comparing these voices for Hindi, so let real users choose between two voices.

Your earlier volume problem has a clear cause. AOSP adds echo cancellation only to the `VOICE_COMMUNICATION` capture path, which is built for voice calls and uses call routing and the separate call-volume slider ([AOSP](https://source.android.com/docs/core/audio/implement-pre-processing)). TTS tagged `USAGE_ASSISTANCE_ACCESSIBILITY` also has its own accessibility volume, separate from media volume ([AOSP commit](https://android.googlesource.com/platform/frameworks/av/+/28d09f0)). If users say TTS is too quiet, or the volume keys do nothing, let them switch TTS to `USAGE_ASSISTANT` or media volume in settings. Start listening only after `onDone`, and record with `VOICE_RECOGNITION`, never `VOICE_COMMUNICATION`. Most of this is engineering inference, so test it on two or three budget phones.

## A human voice speaks at goal boundaries, waits for slow speakers, and stops on "ruko"

People take turns with gaps of about **200 ms in every language studied** ([Stivers et al. via MPI](https://forms.mpi.nl/node/50939)). Voice-agent builders aim for **under 800 ms** from the end of the user's speech to the first sound, and they get there by streaming every stage ([Soniox](https://soniox.com/wiki/voice-agent-latency-budget)). VoiceControl gets a full transcript, waits for the complete Claude reply, and then speaks it, so the gap is several seconds. Cutting latency will feel more human than any change of wording. The order that matters: (1) local commands, which you already have; (2) the screen-fingerprint cache and flow replay; (3) streaming with the `say` field first; (4) a guessed Claude call started on a stable partial transcript and cancelled if the final one means something different. You already say "one moment" on slow steps. Fill shorter gaps with a soft sound or a one-word "haan," and only after about a second.

Elderly speakers pause in the middle of sentences, so a fixed short silence cut-off interrupts them. Systems such as LiveKit start with a short silence window and add a model that judges whether the sentence is finished. They respond after **0.3–0.5 s when the sentence is clearly complete and wait up to 2.5–3 s when it is not**; LiveKit's audio detector supports Hindi ([LiveKit](https://docs.livekit.io/agents/logic/turns/turn-detector)). You can approximate this without new models. Hindi puts the verb last, so a final verb or helper word ("karo," "kar do," "hai," "bhejo") strongly suggests the sentence is complete, while a trailing name or "aur" suggests it is not. Use that to set `EXTRA_SPEECH_INPUT_COMPLETE_SILENCE_LENGTH_MILLIS` per prompt (shorter for yes/no, longer for open requests), or to re-open the mic when a sentence seems cut off. A full on-device turn detector (Pipecat's Smart Turn runs on the phone CPU in under 100 ms) would mean replacing `SpeechRecognizer` with your own audio pipeline ([Pipecat](https://docs.pipecat.ai/server/utilities/turn-detection/smart-turn-overview)). Do it only if cut-offs stay a top complaint.

Keep barge-in off, as now, with one exception. When the app reads something long, such as a message, a list or screen contents, listen only for "ruko," "bas" or "stop," or a tap or volume-key press. Do not stop for any sound, since TVs and family members would trigger it. Stop only after at least 0.3–0.5 s of speech or one recognized word, and resume if no words follow within about 2 s. LiveKit and Vapi handle "false interruptions" this way ([LiveKit](https://docs.livekit.io/agents/build/turns); [Vapi](https://docs.vapi.ai/customization/speech-configuration)). For short prompts, a big on-screen stop button is more reliable.

For wording, follow the main design guides and enforce them in code. Alexa's **"one-breath test"** says a reply should fit in one breath ([Alexa](https://developer.amazon.com/blogs/alexa/post/531ffdd7-acf3-43ca-9831-9c375b08afe0/things-every-alexa-skill-should-do-pass-the-one-breath-test)). Google's confirmation guide sets three levels ([Google](https://developers.google.com/assistant/conversation-design/confirmations)). Use no confirmation for opening, scrolling and navigating. Confirm implicitly, inside the action line, for details: "Rahul ko call kar rahi hoon." Ask an explicit yes/no only for sends, payments and deletes, which you already do, and do not repeat "haan" back. Speak one line at the start of a multi-step task and one at the end ("Ho gaya, message bhej diya"). Stay silent in between unless a step needs the user. Read at most three list items, then ask "aur sunoge?" Make the `say` field optional and empty by default, with a hard character limit. In code, drop any line identical to the one just spoken, and any repeated greeting. For errors and silence, Google's guide gives the escalation ([Google](https://developers.google.com/assistant/conversation-design/errors)). After the first miss, ask again more briefly, in different words, without saying "I didn't hear you." After the second, give an example of what to say. After that, offer big buttons or a caregiver, or go quiet. Never ask "What can I do for you?" more than once per session. After that, show a mic-ready sound and icon.

## The open niche is Indian languages, senior design and safety

The big platforms leave VoiceControl's market open for now. Google Voice Access officially lists English, Spanish, German, Italian, French, Portuguese and Japanese, but **no Indian language**, and users complain about accent errors, cluttered number overlays and battery drain ([Google Support](https://support.google.com/accessibility/android/answer/6151848?hl=en); [Samsung Community](https://r2.community.samsung.com/t5/Discussions/Voice-access/td-p/17803086)). Gemini's app-operating agent launched in March 2026 on the Galaxy S26 and Pixel 10, in **beta in the US and Korea, for apps like Uber and DoorDash**. It runs apps in a separate virtual window, lets the user take over at any time, and requires manual confirmation for purchases ([9to5Google](https://9to5google.com/2026/02/25/gemini-automation-android/)). Siri in India understands Hindi mixed with English for basics such as calls, timers, messages and opening apps, but cannot operate arbitrary apps ([Apple Support](https://support.apple.com/105012)). Samsung's Galaxy AI supports seven Indian languages, but for translation and note-taking, not for operating apps ([SamMobile](https://www.sammobile.com/news/galaxy-ai-supports-7-new-indian-languages-galaxy-s25/)). NPCI's Hello! UPI shows the safe model for voice payments: speak your intent, then always enter the PIN by hand ([TaxGuru](https://taxguru.in/rbi/hello-upi-npci-voice-assisted-upi-experience.html)). The risk is that Google adds Hindi to Gemini's agent. If it does, raw capability stops being an advantage. Senior-focused design, caregiver features and fraud protection would still set the app apart.

Research on the users points the same way. A HelpAge India survey found that **51% of elderly people fear making mistakes with digital tools, 44% feel embarrassed to ask again, and over half rely on children or grandchildren as guides** ([Outlook Money](https://www.outlookmoney.com/news/digital-divide-among-elderly-66-find-digital-tools-too-confusing)). A Microsoft Research India study of semi-literate users found spoken dialogue faster and in less need of help than text interfaces ([Medhi, CHI 2009](https://microsoft.com/en-us/research/wp-content/uploads/2016/02/medhi_chi2009.pdf)). But a study of Gujarat farmers found keypad input finished more tasks than speech, especially for less-educated users ([Patel, CHI 2009](https://hci.stanford.edu/publications/2009/chi2009_patel.pdf)). The lesson: **always offer a non-voice fallback** with big buttons, make "cancel / phir se bolo" safe at any point, and let a grandchild record a flow once that the elder then replays by voice. Your flow recording already fits this. It is also the most Play-safe and cheapest way to run tasks. Both studies are from 2009, and I found no recent study of AI voice agents for Indian seniors, so your own user sessions are the best evidence.

## Conclusion

The research changes what "better" means for VoiceControl. Accuracy no longer depends mainly on which model you use. It comes from plain code around the model: checking that each tap worked, keeping a plan, and remembering how each app behaves. Your flows and saved jobs already hold most of that memory. Speed and cost depend on the same thing: every screen the app has seen before, and every flow a grandchild has recorded, can run without calling Claude. That is cheaper and faster, and it is also the most Play-safe way to work, because Google's policy allows replaying a fixed script that a person defined.

The biggest uncertainty is Google, not the technology. Nothing public says whether an agent whose plan the user approves counts as "autonomous." Google could also bring Gemini's agent to Hindi. Either way, VoiceControl is safest as an honest accessibility tool for people who struggle with phones: one that hears Hinglish well, speaks briefly, never touches a PIN, and stops scams. Build the plan read-back and post-action checks first, because they improve accuracy and policy standing together, and measure every change with your live test harness, because no published benchmark matches your users.
